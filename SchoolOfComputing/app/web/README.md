# RailGuard web application

The React application is the non-technical upload workflow required by NebulaX PS3. A FastAPI
boundary calls the existing `RailGuardPredictor`, converts results to the official task-specific
schemas, validates them, and returns both display data and downloadable CSV text.

The operator workflow also provides an opt-in local history. Each saved analysis records asset ID,
component/location, measurement time, task, real/demo mode, immutable prediction data, model
version, and the SHA-256 identity of the uploaded file. Raw uploads are not copied into the
database.

Asset context is detected as soon as a file is selected. ACV supplies its train number, car model,
car range, and recording time directly; Door supplies its recording time and component type. The
provided Rail and SHM formats contain no train ID or timestamp, so RailGuard uses a clearly
labelled filename-based sample ID and the browser file-modification time. These fallback values are
shown to the operator and remain editable—RailGuard does not invent a train number.

## Local development

Install the Python API and JavaScript dependencies:

```bash
python -m pip install -e ".[api]"
npm --prefix web/frontend install
```

Run the services in separate terminals:

```bash
make api
make web
```

Open `http://localhost:5173`. FastAPI documentation is available at
`http://localhost:8000/docs`.

## Local analysis history

History uses Python's built-in SQLite support and has no additional service or licence cost. The
database is created on first save at `data/railguard.db` and is ignored by Git. Override the path
when necessary:

```bash
export RAILGUARD_HISTORY_DB=/absolute/path/to/railguard.db
```

Analysis results are saved only after the operator reviews the automatically detected asset
metadata and confirms any corrections. Demo
results may be saved, but remain visibly marked as Demo in tables and trends. Asset ID, component
information, and measurement time can be corrected later; prediction content, source hash, mode,
and model version are immutable through the API.

The History workspace supports asset/task/date filtering, asset summaries, Door abnormal-rate and
SHM damage charts, ACV top-car and Rail class sequences, chronological records, and full saved
result inspection.

## Model bundles

Set the applicable variables in `.env` or the shell:

```text
RAILGUARD_DOOR_BUNDLE=outputs/checkpoints/door
RAILGUARD_ACV_BUNDLE=outputs/checkpoints/acv
RAILGUARD_CORRUGATION_BUNDLE=outputs/checkpoints/corrugation
RAILGUARD_SHM_BUNDLE=outputs/checkpoints/shm
```

Only trusted locally produced classical bundles are loaded for Real mode. Operators can explicitly
select an unmistakably labelled demonstration result when `RAILGUARD_ALLOW_DEMO=true`. Demo output
is never described as competition-ready and must not be submitted.

Metric-aligned bundles generated by `scripts/train_competition.py` are discovered automatically
under `outputs/checkpoints/competition/<task>`. Explicit environment variables override these
defaults.

```bash
python scripts/train_competition.py --task all \
  --raw-root /path/to/NebulaX-Hackathon-ProblemStatement/PS3/02_Datasets
```

## Containers

```bash
docker compose up --build
```
